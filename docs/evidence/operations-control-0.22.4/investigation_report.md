# 0.22.4 问题中心控制修复报告

日期：2026-07-31

## 已确认问题

1. 问题详情每五秒下载完整事件历史。两个生产问题的单次详情响应分别约为 16.6 MB 和 15.2 MB。
2. 自动刷新和人工选择可以同时发起详情请求。前端没有请求取消、选择 ID 校验或响应序号保护，旧响应可以覆盖管理员最新选择。
3. 页面依据 `status` 推断按钮，数据库 `allowed_actions` 保存规划能力，两套规则产生了 rejected 可见按钮与 API 动作清单不一致。
4. 管理员意见和实施输入是页面级状态，切换问题后可能沿用到另一个物理问题 ID。
5. 操作错误显示在工作区顶部，操作区缺少就地反馈。
6. `reopen` 接受任意状态，没有完整清理上一轮审批、实施、评估和决策字段。
7. 队列最终失败先写入 `triage_failed`，中文失败摘要在随后步骤写入，读取端可能观察到短暂不完整状态。
8. 受控发布验证使用 `rejected` 结束，造成管理员拒绝的错误业务含义。

## 实施结果

* `allowed_actions` 改为后端状态机生成的当前可执行动作。
* 原规划能力通过 `planned_actions` 保留。
* `reopen` 限制在终态、分诊失败和方案待修订，并清理上一轮可变控制字段。
* 详情响应新增 `event_count`，移除内嵌事件集合。
* 新增 `/api/v1/operations/issues/{issue_id}/events` 序号分页接口。
* 前端使用物理问题 ID 和请求序号保护当前选择。
* 切换问题时清理意见、实施输入、操作反馈和时间线分页状态。
* 操作成功和失败在当前问题操作区显示。
* 队列最终失败由问题服务一次性写入状态、中文摘要、阻断项和审计事件。
* 新增 `validation_completed`，Alembic 0019 迁移历史发布验证记录。

## 验收结论

隔离环境完成 rejected 到 reopen 的真实 API 和页面闭环。重新提交保留原问题物理 ID，追加 `issue.reopened` 事件并进入新一轮分诊。完整时间线仅在展开时分页加载。页面控制台没有 warning 或 error。
